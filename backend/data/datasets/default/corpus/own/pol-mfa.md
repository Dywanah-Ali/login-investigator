# Multi-Factor Authentication Policy

## Requirement and effective date

From 2026-03-02, every account must use multi-factor authentication, referred to as MFA. The standard method is an authenticator app. This applies to staff in the UK office and the US office, remote staff and accounts with administrative permissions. A password alone does not meet the standard unless a named exception has been approved under this policy.

MFA adds a check that is separate from knowing the password. It reduces the usefulness of a password learned by another person. It does not make an unexpected sign-in request safe, and staff must still protect passwords and check what they are approving. The relevant control reference is M1032.

## Setting up the authenticator app

Follow the enrolment instructions available through the intranet or ask the helpdesk to guide you. Install the authenticator app using the approved instructions, then start enrolment from the usual identity provider sign-in route. Do not begin enrolment from a link in an unexpected message.

Complete the pairing step privately and test the app before leaving the setup process. The test should be a sign-in you started yourself. If the test does not work, stop and contact the helpdesk. Do not repeatedly approve prompts to see whether one of them completes setup.

The helpdesk can explain the process without asking for your password or a recovery code. If you change the phone used for the app, arrange the change while you still have access where possible. Do not remove your existing working method before the replacement has been tested.

## Everyday use

Approve an MFA request only when you have just started the corresponding sign-in. Check the details shown by the app. If a request appears unexpectedly, do not approve it. Tell Security through a known channel, including when the request appeared and whether you took any action.

Do not approve a request for someone else, even if they say they are from IT. Do not read an app code to another person. MFA is an individual check and must not become a shared team procedure. Managers must not ask staff to bypass it to meet a deadline.

## Recovery codes

The authenticator's one-time recovery codes are the fallback when the app cannot be used. Generate them during enrolment and keep them private in a secure place separate from the device used for the app. Each code can be used once. A used code must not be relied upon for a later sign-in.

Do not send recovery codes by email, put them in the file share or include them in a helpdesk request. The analyst needs to know whether you can use the recovery process, not the code itself. If codes may have been exposed, contact the helpdesk promptly to arrange replacement and tell Security.

If neither the app nor a recovery code is available, contact the helpdesk for identity verification and recovery assistance. A request for help does not itself authorise removal of MFA. Support must not create an unrecorded exception to complete a call quickly.

## Exceptions

An exception permits one named account to sign in without MFA. It is allowed only when MFA is technically impossible or an emergency role requires access during an MFA service failure. Convenience, travel and a forgotten phone are not sufficient grounds. First consider whether the normal recovery method solves the problem.

Thomas Price (thomas.price) must approve every exception. The request must identify the account, explain the technical or emergency need, describe the intended use and propose a review date. Approval is time-limited and must be recorded in the MFA Exception Register before it is applied.

The register must show the person, username, department, reason, approver, grant date and review date. Security reviews exceptions every quarter and records whether each need still exists. Continued approval requires an explicit decision. An exception must be removed when its justification ends, even if its review date has not arrived.

## Ownership and checks

Security owns this policy and the exception review. IT applies approved changes and confirms that the intended account alone is affected. Staff tell the helpdesk about problems early. System owners must not interpret an MFA exception as permission to grant more access; access groups and their approvals remain separate decisions.
