Overview mapping

  • Shell: dashboard-01's sidebar and header. Header carries the "Synthetic data" badge and the capture date, as in v1. The capture date comes from the dataset facts response.
  • Tiles: the block's four KPI cards, v1's four figures. The failed share is computed in the frontend from the two raw numbers, as ticket 01 says.
  • Charts: stacked bars for sign-ins per hour, horizontal bars for top IPs. Both Recharts via the chart component. The block's interactive chart and its 7d/30d/90d toggle are removed, because the toolbar already holds the date range. This answers the question handed over from ticket 05.
  • Empty state: one message component reused on all three dashboard screens.

Decision 2. Where the evidence of a selected alert opens

  • Side panel: clicking a row opens a panel on the right (shadcn Sheet) with the evidence table, "Open in Log explorer" and "Investigate". The list stays in view. This is the pattern dashboard-01 uses for its row details.
  • Below the table: v1's placement. Simpler, but on a long list the evidence sits under the fold and the reader loses the row they clicked.

Each rule's title, "fires when" and assumption, from the same text as rules.py, served by the API.

Alerts mapping

  • Table: the tasks example's table. Columns are v1's seven. Sorted newest first by the core. The frontend cuts names to three and adds "and N more".
  • Summary line: counts per rule computed in the frontend from the list.
  • Security: summary, IPs and users are log-derived and appear only in table cells. React renders text content escaped by default, so a cell cannot become markup. The rule is kept by never passing log fields through a markdown renderer or dangerouslySetInnerHTML.
  • "Investigate": a link to the Investigator with the alert's summary as the question, as in v1's optional button. Confirm in ticket 09 what the link carries.

Decision 3. Where the filter state lives

  • In the URL: the filters are the page's search parameters, such as ?from=2026-10-01&to=2026-10-08&outcome=failure&country=RU. Switching screens keeps them. Reload keeps them. "Open in Log explorer" becomes a plain link, and a filtered view can be pasted into a ticket. Each API request takes the same parameters.
  • In memory only: a React state shared by the three screens. Simpler to write, lost on reload, and the explorer jump needs its own mechanism.

Log explorer mapping

  • Toolbar: the shared filters plus the IP box, on this screen only. The IP is validated in the browser before the request and refused again by the API.
  • Counts strip: five tiles from the core's summary.
  • Table: the same tasks table pattern as Alerts, seven columns, paged instead of v1's scroll box. Paging is a presentation choice and stays in the frontend. The count line still says every row is there.
  • CSV: a download endpoint on the API with the same filter parameters, so the file and the table come from the same core search.
  • Security: the planted S5 row is shown as plain cell text, as drawn above.

Decision 4. Where the past investigations list sits

  • Second column inside the page: the sidebar stays navigation on every screen. The Investigator page has its own left column with "New investigation" and the list. Same shape as every chat product.
  • Inside the app sidebar: v1's placement. The sidebar would change content when you enter the Investigator, and the navigation would have to move or shrink.

Investigator mapping and security rendering

  • Chat: the official message and bubble components inside a message-scroller. The stream arrives over SSE as ticket 06 decided; tool events drive the progress line and the Tools used panel.
  • Tools used: a Collapsible under each answer, with the Asked and Found lines from the core, the rows in a table, and the raw JSON behind a Switch.
  • Report: a Card with the fixed fields. The report button sends the fixed sentence into the chat. The PDF is a link to the API's download endpoint.
  • Security rendering, settled here: agent answers and report fields are rendered as text nodes with line breaks kept (white-space: pre-wrap), exactly as v1's as_plain_text does. No markdown library at all, so there is nothing to configure and no link or image can appear. Log fields appear only in table cells. The repository rule becomes: no dangerouslySetInnerHTML and no markdown renderer anywhere in the frontend, checked by a lint rule or a grep test. This graduates the "Security rendering in React" fog without a new ticket.
